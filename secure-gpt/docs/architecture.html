SecureGPT: Enterprise DLP Platform

Comprehensive Feature Update Specification & Technical Architecture Design

01 Executive Summary

This technical document maps out the upgrade from SecureGPT (currently an independent user DLP application) to a robust Enterprise DLP Platform.

The goal is to allow Organizations to register, centrally enforce data protection policies, and manage team members via granular Role-Based Access Control (RBAC). Standard (independent) users must be able to continue using the application with absolute control over their own policies, while Organization-bound users automatically transition to a compliant, controlled state.

Core Design Constraint

Enterprise administrators must hold ultimate veto power. Any preexisting policies owned by a user automatically transition to a read-only lock state upon that user joining an Organization. Legacy policies then become fully editable and deletable by the Organization's Admin.

02 Detailed Feature Specifications

1. Organization Registration

Any system user or guest will be able to register a new Organization. This action provisions a tenant space in the system.

  • Creates an entry in the organisations table.
  • Generates a default, customizable dynamic RBAC schema for the Organization.
  • Automatically binds the creator to the organization (org_id field) and assigns them the default ORG_SUPER_ADMIN role.
  • Domain Validation: Checks the admin_email domain. Common email domains (e.g. gmail.com, yahoo.com, outlook.com, hotmail.com, etc.) are strictly blocked. Only custom corporate domains are allowed for registering organizations.

2. Invitation & Auto-Enrollment Pipeline

Org Administrators can invite users via email. Domain Restriction: The system enforces that the invited user's email domain matches the organization's domain (established during organization registration). Invitations sent to mismatched domains will be rejected by the API.

If the domain matches, the system dynamically alters the pathway depending on the user's status:

Scenario User Status System Action
New User Email is NOT registered in SecureGPT. Generates an invitation token, saves it, and sends a registration link. Upon registration, the user is bound to the org_id.
Existing User Email is ALREADY registered. Auto-Enrollment: Updates the user's org_id directly in the database. Locks the user's personal policies (sets is_locked_by_org = True). No accept link required. Sends an informational notification email.

3. Dynamic Scoping of Policies

Policies are evaluated dynamically based on the user's organization state:

Independent Users

  • org_id is NULL.
  • Has full CRUD permissions over their own policies.
  • Can toggle, modify, or delete custom Regex patterns and sensitivity thresholds.

Organization Users

  • org_id is bound to an Organization.
  • All legacy personal policies set is_locked_by_org = True.
  • The user loses write/update/delete permissions over these policies.
  • Organization policies are automatically pushed down and active on all organization members.

03 Database Schema Changes (SQLAlchemy)

The backend requires updates to the SQLAlchemy definitions to transition from schema-only stubs to active relation management.

Modified Models

We modify Organisation, User, and Policy to introduce relations and lock mechanisms.

# backend/app/models/org.py
class Organisation(Base):
    __tablename__ = "organisations"

    id: Mapped[str] = mapped_column(String, primary_key=True, default=lambda: str(uuid.uuid4()))
    name: Mapped[str] = mapped_column(String(255), nullable=False)
    admin_email: Mapped[str] = mapped_column(String(255), nullable=False)
    plan: Mapped[str] = mapped_column(String(50), default="free")
    is_active: Mapped[bool] = mapped_column(Boolean, default=True)

    # Relationships
    users: Mapped[list["User"]] = relationship("User", back_populates="organisation")
    policies: Mapped[list["Policy"]] = relationship("Policy", back_populates="organisation")
    roles: Mapped[list["Role"]] = relationship("Role", back_populates="organisation")
# backend/app/models/policy.py
class Policy(Base):
    __tablename__ = "policies"
    # ... legacy fields (name, description, pattern, action) ...

    user_id: Mapped[str] = mapped_column(String, ForeignKey("users.id"))
    org_id: Mapped[str | None] = mapped_column(String, ForeignKey("organisations.id"), nullable=True)
    is_locked_by_org: Mapped[bool] = mapped_column(Boolean, default=False)

    # Relationships
    user: Mapped["User"] = relationship("User", back_populates="policies")
    organisation: Mapped["Organisation | None"] = relationship("Organisation", back_populates="policies")

New Dynamic RBAC Tables

To support dynamic roles with module-level permissions, we introduce Role, RolePermission, and UserRoleAssignment.

# backend/app/models/rbac.py
from enum import Enum as PyEnum

class PermissionModule(str, PyEnum):
    POLICY = "POLICY"
    USER_MANAGEMENT = "USER_MANAGEMENT"
    AUDIT_LOGS = "AUDIT_LOGS"
    BILLING = "BILLING"

class Role(Base):
    __tablename__ = "roles"

    id: Mapped[str] = mapped_column(String, primary_key=True, default=lambda: str(uuid.uuid4()))
    org_id: Mapped[str] = mapped_column(String, ForeignKey("organisations.id"), nullable=False)
    name: Mapped[str] = mapped_column(String(255), nullable=False)
    is_system_default: Mapped[bool] = mapped_column(Boolean, default=False)

    organisation: Mapped["Organisation"] = relationship("Organisation", back_populates="roles")
    permissions: Mapped[list["RolePermission"]] = relationship("RolePermission", back_populates="role", cascade="all, delete-orphan")

class RolePermission(Base):
    __tablename__ = "role_permissions"

    id: Mapped[str] = mapped_column(String, primary_key=True, default=lambda: str(uuid.uuid4()))
    role_id: Mapped[str] = mapped_column(String, ForeignKey("roles.id"), nullable=False)
    module: Mapped[PermissionModule] = mapped_column(Enum(PermissionModule), nullable=False)
    
    can_create: Mapped[bool] = mapped_column(Boolean, default=False)
    can_read: Mapped[bool] = mapped_column(Boolean, default=False)
    can_update: Mapped[bool] = mapped_column(Boolean, default=False)
    can_delete: Mapped[bool] = mapped_column(Boolean, default=False)

    role: Mapped["Role"] = relationship("Role", back_populates="permissions")

class UserRoleAssignment(Base):
    __tablename__ = "user_role_assignments"

    user_id: Mapped[str] = mapped_column(String, ForeignKey("users.id"), primary_key=True)
    role_id: Mapped[str] = mapped_column(String, ForeignKey("roles.id"), primary_key=True)

04 Core Backend REST Endpoints

Below are the REST endpoints designed to control the Organization, Invitations, Policies, and Dynamic Roles.

1. Organization Registration

POST /api/v1/orgs/register

// Request Payload
{
  "name": "Acme Corp",
  "admin_email": "admin@acme.com"
}

// Success Response (201 Created)
{
  "org_id": "a4d8c89b-730a-4fb4-bf4a-d6981cfef7b1",
  "name": "Acme Corp",
  "created_at": "2026-07-09T11:21:00Z"
}

// Error Response (400 Bad Request - Common email used)
{
  "detail": "Organizations must be registered using a custom business domain. Public email providers (gmail.com, yahoo.com, outlook.com, etc.) are not allowed."
}

2. Team Invitations

POST /api/v1/orgs/invite

// Request Payload
{
  "email": "employee@acme.com",
  "role_id": "role-default-user-uuid"
}

// Response (200 OK - Auto-Enrolled Existing User)
{
  "email": "employee@acme.com",
  "status": "auto_enrolled",
  "policies_locked": 3
}

// Response (201 Created - New User Invitation Sent)
{
  "email": "new_hire@acme.com",
  "status": "invitation_sent",
  "token": "inv-tok-9821379"
}

// Response (400 Bad Request - Mismatched Domain)
{
  "detail": "Cannot invite users from external domains. Invited email domain must match the Organization's registered domain (acme.com)."
}
